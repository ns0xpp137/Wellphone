# 机灵（Wellphone）

**移动端后台智能体运行环境**

> 智能体在独立的虚拟显示区域中完成跨应用任务，用户可同时正常使用设备；当任务需要用户介入时，智能体将当前操作界面完整移交给用户，处理完毕后继续在原进度上执行。

机灵不依赖云手机、外接设备、前台抢占方案，也不依赖任何第三方授权应用。它运行在用户当前设备上，为智能体提供一块独立且不可见的显示区域。所需 shell 权限由应用自行完成一次无线调试配对获取，无需 root、无需安装其他应用、无需连接电脑。

## 一、产品定位

移动端智能体的常规实现方式存在同一类限制：智能体一旦开始执行，用户就必须让出设备。其结果通常是被抢占前台、被抢占输入法，或因等待而出现整机卡顿。

机灵采用另一种架构：**为智能体分配独立的虚拟显示区域**。

- 用户在主屏正常使用其他应用，不受智能体执行过程影响
- 智能体在后台虚拟显示区域中启动目标应用、检索信息、填写表单
- 用户可通过角落的镜像窗口观察智能体的操作画面，并通过思考流查看其每一步的决策依据
- 当任务涉及支付、登录或验证码等敏感环节，智能体会主动发起移交：用户点击「接管」后，智能体正在操作的界面完整呈现于主屏；处理完毕点击「返回后台」，智能体从原进度继续执行

## 二、运行模式

| 对比项 | 工作区模式（默认） | 协同模式 |
|---|---|---|
| 智能体感知范围 | 独立虚拟工作区 | 用户当前主屏 |
| 是否影响主屏界面 | 否 | 仅在条件满足时执行动作 |
| 典型任务 | 在电商/本地生活应用中检索并完成下单 | 打开相机，在特定目标出现时触发拍摄 |
| 启用方式 | 始终可用 | 应用内「主屏监控」开关，默认关闭 |

协同模式用于「满足特定条件后触发动作」类需求。相机取景画面、直播流等内容仅存在于主屏，虚拟工作区中不可获取，因此该类任务必须基于主屏画面执行。

## 三、技术选型

产品需要在单台非 root 设备上同时满足「后台并行执行」与「不干扰用户」，可选空间受 Android 平台能力约束。以下为关键选型及取舍依据。

| 维度 | 选型 | 主要备选 | 选择理由 |
|---|---|---|---|
| 平台与语言 | Android 原生 Java（API 30+），不使用跨端框架 | Flutter / React Native | 需要直接调用 `DisplayManager`、`SurfaceControl`、无障碍服务与 shell 通道，跨端框架在每一处都要额外编写原生桥接，收益为负 |
| 构建链 | 自建 `build.py`（aapt / d8 / zipalign / apksigner） | Gradle + AGP | 单模块、无第三方依赖，一次构建约 20 秒；四变体只需替换 manifest 字段，不必维护四套构建配置 |
| 并行执行载体 | `VirtualDisplay` + 独立进程 `DisplayHost`（`app_process`，shell 身份） | 云手机 / 分屏 / 后台直接启动 Activity | 云手机存在网络往返与账号成本；分屏占用用户屏幕；Android 10+ 限制后台启动 Activity。虚拟显示区域是唯一既不占用用户屏幕、又可常驻的方案 |
| 输入注入 | shell `input -d <displayId>` | 无障碍 `ACTION_CLICK` / 图像坐标点击 | `input -d` 精确落屏且不抢占主屏输入法；无障碍注入在未导出节点树的应用上直接失效 |
| 屏幕采集 | `SurfaceControl` / `ScreenCapture` 隐藏 API（以 shell 身份运行以规避隐藏 API 限制） | `MediaProjection` | `MediaProjection` 需用户逐次授权录屏，且部分 ROM 上无法指定采集哪块 display |
| 权限获取 | 应用内无线调试配对（自研 adb 客户端） | root / Shizuku / 电脑侧 adb | 不要求 root、不要求安装第二个应用、不要求连接电脑；Shizuku 通道保留为可选 |
| 模型分工 | 豆包（视觉主循环）+ DeepSeek（文本路由），Anthropic 与 OpenAI 两套协议并存 | 单一多模态大模型 | 意图路由只需文本，用最低成本模型完成；主循环必须视觉，可按实测结果切换 |
| 记忆机制 | `SharedPreferences` + 技能库（带参动作序列） | 云端向量库 | 单机场景无需引入服务端；技能库把已跑通的路径转为确定性执行，减少模型调用 |
| 安全边界 | 代码闸门（相机 / 支付 / 输入框三类硬拦截） | 系统提示词约束 | 实测提示词对模型不构成有效约束，涉及资金与用户干扰的边界必须由代码判定 |

感知链路采用三层混合：无障碍节点树 → 视觉 Set-of-Mark → Intent 直达，按目标可达性逐级降级。纯视觉方案对坐标换算与画面缩放高度敏感（见 5.7）；纯无障碍方案在未导出节点树的应用上直接失效；Appium / UIAutomator2 依赖主机侧 adb 连接，无法在设备内常驻，也就无法与虚拟显示区域、记忆区、账号体系集成。

## 四、核心设计决策

以下八项为架构层面的关键决策。

### 4.1 接管的语义是任务迁移，而非新建实例

常规做法是在主屏重新启动目标应用，但该做法会带来三个问题：

- 应用状态丢失（检索结果清空、导航停留在加载页）
- 后台产生重复实例
- 用户看到的是应用首页，而非智能体已执行到的界面

正确做法是调用 `am display move-stack <taskId> <displayId>`，**将任务栈本身迁移至另一显示区域**。同一实例切换显示载体，应用状态保持原样。

```
126（虚拟显示区）→ 点击接管 → 0（主屏）→ 点击返回后台 → 126（虚拟显示区）
```

### 4.2 按任务特性选择感知方式，避免逐帧视觉推理

- **相机条件监控（如等待目标出现）**：画面为 30fps，而单次视觉模型调用耗时 1.5–2 秒。若采用「每两秒采样一帧」的策略，目标早已离开画面。此类需求应使用本地轻量目标检测（单帧约 10ms），模型仅用于参数调整等低频决策环节。
- **直播弹幕响应（如识别口令后发送弹幕）**：该需求不涉及视觉，所需能力为流式语音识别与关键词匹配。

在架构设计中识别出「此处不应调用大模型」，其价值高于新增一项功能。

### 4.3 无障碍不可达的目标，改用 Intent 直达

部分应用的控件未导出至无障碍节点树（例如部分定制 ROM 记事本的「新建」按钮），此类目标无法通过视觉定位稳定命中。但其编辑页 Activity 可被直接启动：

```
am start -n cn.nubia.notepad.preset/cn.nubia.notepad.NotePadEditorActivity
```

处理方式为：枚举目标应用的 Activity 清单 → 依据名称关键词匹配目标页面 → 通过 Intent 直接跳转，从而绕开 UI 导航与坐标推断。

该方案同时消除了一个高风险场景：智能体无法点击新建按钮时，退化为在既有笔记内输入文字，导致用户原始内容被覆盖。采用 Intent 直达后，智能体无需触碰任何既有条目。

### 4.4 动作执行成功不等于目标达成

点击快门返回 `ok`，但照片并未产生。仅依据动作回执进行判断不足，必须引入结果校验：

```
点击快门 → 比对相册最新文件名 → 若无变化则补发系统相机键 → 再次校验
```

对应日志示例：`快门点击未生效 → 补发系统相机键，结果：已生成 IMG_...jpg`

> 相机快门通过屏幕坐标点击时稳定性不足（模型输出的归一化坐标经换算后存在偏差，无障碍 `ACTION_CLICK` 亦不一定生效）。系统相机键 `input keyevent 27` 为可靠触发方式。

### 4.5 意图路由交由模型判定，不使用关键词规则

「用户输入属于任务还是提问、是否需要读取其屏幕」这类判断，在早期版本中通过关键词匹配实现：

```java
String[] keys = {"当", "一旦", "出现", "就拍", ...};
```

该方案存在明显误判。例如「打开微信，查看某联系人的聊天记录，其中出现任意商品即前往京东购买」会因命中「出现」被判定为需要主屏监控的任务，从而被强制要求开启主屏监控——而它实际是一次普通的跨应用任务。

现改为通过单次**纯文本模型调用**完成路由，返回严格 JSON：

```json
{"type":"task|question|correction|control", "mode":"background|main", "app":"...", "reply":"..."}
```

- `question`（提问）→ 直接回答，不创建显示区域、不截图、不调用视觉模型
- `task`（任务）→ 进入主循环，由 `mode` 决定使用工作区或主屏监控
- `correction`（纠正）→ 写入记忆区
- `control`（停止/接管）→ 直接执行，不经过模型判定

**关键工程约束**：当模型不可用（未配置密钥、超时、返回非法 JSON）时，**回退至规则路由**。路由位于链路最前端，其故障不应导致应用整体不可用。

同时带来成本收益：单次路由消耗数十 token，主循环单次消耗数千 token，最简任务交由成本最低的模型处理。

### 4.6 程序化记忆：将执行路径沉淀为技能

智能体的重复推理存在浪费——移动端操作路径具有高度可复用性（启动应用 → 点击搜索 → 输入 → 提交）。

因此仅在任务**确认成功**后（成功门控，以模型判定 finish 的时刻为准），将该轮已跑通的动作序列固化为技能：

```
技能 = { 应用, 动词, 起始页面指纹, 动作序列, 成功次数, 失败次数 }
```

同类任务再次进入时，优先检索技能库；命中则按记录执行，跳过模型调用。

三项必须保证的约束：

- **技能是带参数的函数，而非固定脚本。** 动作序列中以 `{q}` 占位，否则首次记录的「搜索火锅」会在下次「搜索烤肉」时被原样复用。
- **连续成功两次方可转正。** 移动应用会迭代改版、会弹出权限对话框，单次成功不足以证明路径稳定（Voyager 在 Minecraft 环境中的单次即写入策略，建立在确定性环境之上）。
- **支持优雅降级。** 命中后仍需逐步校验，一旦偏离立即放弃并交还模型；连续两次失败自动淘汰，对应缓存失效的处理方式。

该设计参考 Voyager（2023）的技能库思路，以及 Agent S4《Evolving Agent Interfaces》（2026）中「智能体从任务经验中演化其使用的接口」的论述。沉淀所得的技能，本质上是为模型新增了一个高层动作。

### 4.7 无干扰约束必须由代码强制，不能依赖提示词

以下三项约束曾全部写入系统提示词，但在实际执行中均未生效：

| 约束 | 提示词声明 | 实际表现 | 最终方案 |
|---|---|---|---|
| 禁止点击相机/拍照入口 | 已声明 | 仍发生点击，触发应用内拍照识图页，闪光灯亮起 | 在点击分发前判定目标元素，命中相机类元素直接拒绝 |
| 支付页禁止继续操作 | 已声明 | 尝试点击「极速支付」，支付信息完整时将直接扣款 | 支付页设置强制闸门，仅放行 `Back` / `Take_over` / `finish` |
| 禁止优先点击输入框 | 已声明 | 仍点击搜索框，导致主屏输入法被抢占 | 判定元素 `editable` 属性，命中则拒绝并提示改用 `Type` 动作 |

结论：**凡涉及用户干扰或真实资金支出的约束，均不能依赖模型自觉**。提示词属于软约束，模型为完成任务会绕过；代码闸门属于硬约束。

### 4.8 干扰来源包括被操作应用自身

早期对「无干扰」的定义为「不触碰用户主屏」。实测表明该定义不完整：智能体点击进入某应用的拍照识图页后，**由该应用自行调用系统相机**并点亮闪光灯，用户感知为设备自行开启了补光灯，而本系统未发送任何相机指令。

因此边界需重新界定：

> 无干扰 = 本系统不操作主屏 **且** 被操作应用不执行干扰性行为。

后一层约束只能通过「禁止进入该类页面」间接实现。

## 五、关键技术问题与解决方案

### 5.1 跨显示区域启动的权限根因

现象为「程序未能在虚拟屏打开」。排查后确认根本原因并非应用不支持分屏，而是 **display 的属主归属**：

- 虚拟显示区域由 `DisplayHost` 以 shell 身份（uid 2000）创建
- 目标应用运行于 uid 10xxx
- Android 的 `isCallerAllowedToLaunchOnDisplay` 不允许非属主向该显示区域发起 `startActivity`，调用被静默回退至主屏

**解决方案：所有启动请求统一由 shell 下发**（shell 为该 display 的属主）：

```
am start --display N -f 0x18000000 -n <pkg>/<组件>
```

组件名通过 `PackageManager.resolveActivity(MAIN/LAUNCHER)` 实时解析，应用内 Intent 仅作为兜底方案。

### 5.2 跨应用执行的三个阻断点

早期跨应用任务无法完成（「先微信再京东」中，京东被解析为微信），由三处实现缺陷共同导致：

1. **`forcedPkg` 未在使用后清空**：该字段为跨任务存活的 `volatile` 字段，导致后续所有 `Launch` 均返回首个应用的包名
2. **单应用上下文**：`currentPkg` 仅有一个实例，节点清单、SoM 标注、直达页面均绑定该包
3. **缺少跨应用信息传递机制**：商品名称无法从微信传递至京东

对应处理：

- `forcedPkg` 使用后立即清空
- **应用上下文跟随前台窗口动态推导**（`focusedPackage()` 取层级最高的应用窗口），切换应用后节点清单自动更新。该方案不依赖应用适配代码，对任意数量应用一致生效
- **信息槽**：新增 `do(action="Remember", key="商品", value="...")`，并在每步提示中附带【已记住的信息】
- 多应用场景下，按**任务中出现的先后顺序**选取第一个，替代此前基于 HashMap 顺序的选取方式（该方式每次结果不一致）

### 5.3 虚拟显示区域与主屏需保持同尺寸同密度

接管过程中出现字体大小跳变。根因是虚拟显示区域为 720×1280@360dpi，主屏为 1216×2688@520dpi，任务跨屏时触发配置变更，Activity 重新布局。

**解决方案：虚拟显示区域直接采用主屏的像素尺寸与密度**，抓取的帧再等比缩放至 720 宽后送入模型（上传体积不变）。

> 附加约束：缩放**必须保持等比**。将真实比例 1216:2688（0.45）强制缩放为 720×1280（0.56）会导致画面变形，模型所见的界面本身即为错误信息——这是「点击位置偏移至相邻元素」的主要原因。

### 5.4 长任务阻塞：JSON 控制字符

任务执行至第 21 步后开始返回空输出。服务端报错：

```
JsonMappingException: Illegal unquoted character ((CTRL-CHAR, code 9))
  → messages[44].content
```

`code 9` 对应 TAB 字符，来源于应用内的笔记标题内容。项目自定义的 `jsonStr()` 仅转义 `"`、`\`、`\n`、`\r`，遗漏了 0x00–0x1F 范围内的其他控制字符。

**阻塞具有持续性的原因**：该条含 TAB 的消息已进入对话历史，后续每一步均发送同一份非法 JSON，第 21/22/23 步返回完全一致的 400 错误，直至步数耗尽。

修复涉及三处：补全 `jsonStr` 的字符转义、在节点 label 源头做清洗、对 400 错误不再无条件重试（第 1 次丢弃最后一步，第 2 次仅保留最近一屏，第 3 次交由用户处理）。

### 5.5 不支持的动作不应判定为模型能力问题

模型输出 `Long_press`（当前未实现）→ 返回 `err` → `fails++` → 连续 2 次后**主模型被降级**。

但「模型使用了未实现的动作」属于实现侧缺口。降级至能力更弱的模型只会提升其输出不支持动作的概率，形成**负向循环**：doubao → glm → glm45，逐级劣化直至无法执行。

现改为返回 `unsupported` 状态，并将可用动作列表完整回传至模型，**不计入失败次数、不触发模型切换**。

### 5.6 免第三方依赖的授权路径：内置 adb 通道

机灵的 shell 能力由应用自身实现，不依赖任何外部授权应用。`BuiltinShell` 直接实现 adb 客户端，在应用内与系统 adbd 完成握手，从而获得 shell（uid 2000）权限。协议实现取自 RikkaApps/Shizuku（Apache-2.0），仅引入 `AdbPairingClient`、`AdbClient`、`AdbKey`、`PreferenceAdbKeyStore` 等 6 个源文件，不依赖 Shizuku server。

该能力基于 Android 11 及以上版本提供的无线调试机制：

1. `AdbPairingClient` 使用配对码与 adbd 完成 adb pair（SPAKE2 + TLS）
2. 配对成功后由 `AdbClient.connect()` 接入 adbd
3. `shellCommand()` 下发的命令以 shell 身份执行，行为与 Shizuku 通道完全一致

**配对交互受两条系统行为约束**，与实现偏好无关：

- **配对码必须在不离开系统页面的前提下输入。** 系统的「使用配对码配对设备」页面一旦退到后台，配对码立即刷新。因此输入框被放入通知栏（`RemoteInput`），用户下拉通知栏输入即可，系统页面保持前台，配对码不失效。
- **端口不由用户填写。** 通过 mDNS 自动发现 `_adb-tls-pairing._tcp`（配对端口）与 `_adb-tls-connect._tcp`（连接端口）。当局域网内存在第二台开启无线调试的设备时，必须校验服务名与 IP 是否与刚配对的设备一致，否则会连到其他设备并报 `SSLV3_ALERT_CERTIFICATE_UNKNOWN`。

此外，部分 ROM 在插入 USB 数据线时不再广播 `_adb-tls-connect`。若配对成功后 15 秒内仍未发现连接端口，界面会提示拔线重试，避免用户无反馈地等待。

**通道选择**：`ShellChannel.available()` 同时接受两条通道——Shizuku 通道就绪时优先使用，否则回退至内置通道（`execFast`，单次握手约 200–300ms）。两者对上层接口等价，业务代码无需区分，因此是否安装 Shizuku 由用户自行决定，不影响功能完整性。

实现层面的约束：

**① 不得在主线程调用。** 该通道本质是网络连接，Android 会直接抛出 `NetworkOnMainThreadException`：

```
点击「接管」→ takeover() 于主线程 → preGrant()/takeoverMoveToMain() → 调用 shell
                                                    ↓
                                   NetworkOnMainThreadException
                                                    ↓
                      execFast 返回 null → 未找到任务 → 兜底「新建实例」
```

用户侧表现为「接管后重新启动了应用、操作记录丢失」。所有 shell 调用均需移入后台线程。

**② 命令通道每次新建连接，不复用。** 为降低握手开销曾引入「共享 AdbClient」复用优化，但 `DisplayHost` 的常驻进程已占用一条连接的 shell 流，复用导致协议错乱（`not A_WRTE` / `EOFException`），**后续所有命令均失败**，表现为虚拟显示区域内无法启动任何应用。现改为每次新建、使用后立即关闭，以一次握手开销换取通道稳定。

**③ 宿主进程通道必须常开。** 启动 `DisplayHost` 的命令不做后台化（不使用 `&` / `setsid`），并保持该连接不关闭——连接断开会被连带终止宿主进程，且后台化形式下进程静默退出、无法获取报错。

### 5.7 Set-of-Mark 标注的坐标系错位

现象为模型「能识别控件但点击位置偏移」。排查结果为：Set-of-Mark 编号框使用**屏幕像素坐标**（0..1216），却直接绘制在**720×1592 的缩略截图**上，导致大部分标注框落在画布之外，其余标注亦整体错位；模型据此复制的标注框中心点因此不落在目标控件上。

**当画布坐标与目标坐标不在同一尺度时，必须显式换算。** 该类问题的隐蔽性在于表现始终为「识别正确、点击不准」，容易被误判为模型能力不足。

## 七、已知限制

- **首次无线调试配对无法省略**。这是 Android 的安全边界：获取 shell 权限必须先完成一次 adb 配对授权，应用无法自我提权。配对全程在应用内完成（配对码在通知栏输入），不需要安装第二个应用，也不需要电脑。配对后密钥持久保存，此后启动应用直接复用，无需重复配对。
- **无线调试需保持开启**。关闭无线调试或设备重启后，adbd 的监听端口可能变化，已保存的连接将失效，需重新执行一次配对流程。
- **延迟为秒级**，不适用于要求 200ms 内响应的场景；该类场景应改用本地检测方案。
- **部分应用未导出无障碍节点树**（如部分短视频应用），仅能依赖画面坐标，可靠性低于节点树可读的应用。
- **虚拟显示区域与主屏同尺寸**，抓帧后需缩放，存在固定开销。
- 步数上限可在 20–50 之间配置，单步约消耗 1.3k token，成本由使用者承担。
- **启动应用的瞬间，主屏正在使用的输入法会被收回（键盘消失）**。原因：Android 的 IME 为全局单例，虚拟显示区域中刚启动的 Activity 取得窗口焦点后，系统将主屏的 IME 请求路由至该窗口（`dumpsys input_method` 中可见 `mServedView` 变为桌面 DecorView、`mInputShown=false`）。这是**双屏架构的系统级限制，不属于实现缺陷**；除文本输入类操作外（浏览视频、翻页、查看图片），其余场景不受影响。缓解措施如下：

  - 文本写入统一使用无障碍 `ACTION_SET_TEXT`（无需焦点、不触发 IME），不使用剪贴板粘贴——粘贴需先点击输入框，该动作本身会抢占 IME
  - 代码层面禁止点击任何输入框，引导智能体直接使用 `Type` 动作写入
  - 演示「用户正常使用设备」场景时，避开正在进行文本输入的状态

## 八、构建与运行

### 运行环境依赖

- Android 11（API 30）及以上
- 一次无线调试配对（用于获取 shell 权限）
- 视觉大模型 API（同时支持 Anthropic 协议与 OpenAI 协议）

Shizuku 属于**可选**通道：设备上已安装并授权 Shizuku 时优先使用该通道，否则自动使用内置 adb 通道。两条通道的能力与上层接口完全一致，功能不受是否安装 Shizuku 影响。

### 首次配置

> shell 权限是跨显示区域启动、注入触摸事件、读取无障碍配置的前提。未完成配对时，应用可正常打开界面，但无法执行任务。

1. 安装并打开机灵
2. 点击「**内置配对**」，应用开始通过 mDNS 搜索配对服务
3. 进入 **系统设置 → 开发者选项 → 无线调试**，开启后点击「**使用配对码配对设备**」，屏幕显示 6 位配对码（保持该页面在前台）
4. 下拉通知栏，在「机灵 内置配对」通知中直接输入配对码
5. 配对成功后，应用自动发现连接端口并启动工作区（虚拟显示区域）
6. 点击「**一键准备**」：应用经 shell 自动写入无障碍服务配置并完成绑定，校验虚拟显示区域，开启镜像窗
7. 此后启动应用直接复用已保存的连接，无需重复配对

> 不要在应用内输入配对码——离开系统的配对页面会导致配对码刷新，通知栏输入即为此设计。若第 6 步无障碍服务未绑定成功，可在 **系统设置 → 无障碍 → 机灵** 中手动开启一次。

若设备已安装并授权 Shizuku，可跳过上述配对步骤，直接点击「一键准备」由应用自动完成服务授权、无障碍绑定与虚拟显示区域创建。

## 九、API Key 配置

源码中**不包含任何密钥**——`PROVIDERS` 的 `key` 字段为空字符串，于运行时注入。

**推荐方式：在应用内点击「API Key」按钮**，分别填写两个输入框：

| 输入框 | 用途 | 说明 |
|---|---|---|
| 豆包（火山方舟） | 主循环——读取截图、输出动作 | 需具备视觉能力 |
| DeepSeek | 意图路由、问题回答 | 纯文本即可，成本低、响应快 |

两项均仅保存在本机 `SharedPreferences` 中，不上传。按需填写，修改后立即生效。

> 早期版本通过在 `/sdcard/Android/data/<包名>/files/` 下写入 `llm.json` 完成注入。
> 实测在目标设备上应用无法读取该目录（adb 可写入，应用侧读取失败），因此改为通过应用界面配置。
> 文件注入路径作为兜底方案保留，但不推荐使用。

配置完成后，点击「大脑」按钮可在 doubao / deepseek 之间切换主循环所用模型，用于实测对比速度与准确率。

未配置密钥时，应用不会静默失败，而是明确提示「未配置 API key」并指引配置入口，避免出现连续 401 降级而无法定位根因的情况。

`.gitignore` 已包含 `*.apk`、`*.jks`、`classes*/`、`dex*/`、`variant/`、`build.out`，以及**含密钥的 `llm*.json` 与真机日志**。

## 十一、隐私与安全

- 主屏监控**默认关闭**。关闭状态下，智能体无法获取主屏内容。
- 启用后，通知栏常驻提示「主屏监控已开」。
- 监控类任务仅在**用户明确要求启动时**才会打开目标应用。对于「屏幕上一旦出现指定内容即截图」这类纯监控需求，系统不会主动启动相关应用。
- shell 权限仅来自用户主动完成的一次无线调试配对，应用不做任何自我提权。adb 配对密钥与连接信息保存于本机 `SharedPreferences`（`adbkey` / `builtinshell`），不对外传输。
- 配对通道的有效期由用户控制：关闭无线调试即断开，应用无法自行恢复。
- API Key 仅存储于本机，不上传至任何服务端；仓库中不含任何密钥。
