# 机灵 / Wellphone

**让 agent 在你手机的后台工作区里替你办事——你照常用手机，需要你的时候，它把正在操作的那个界面整个搬到你面前。**

不是云手机，不是第二台设备，不是无障碍抢前台。是同一台手机上，一块你看不见的屏幕。

> App 名「机灵」，仓库沿用早期工程名 Wellphone。

---

## 一、它解决什么

手机 agent 的主流做法都有同一个毛病：agent 一动手，用户就得让位。要么它抢走前台、要么抢走输入法、要么卡住整机。

Wellphone 的做法是：**给 agent 开一块它自己的屏幕**。

- 你在主屏聊微信、刷视频，完全不受影响
- agent 在后台那块虚拟屏里打开美团、搜东西、填表单
- 你能在屏幕角落看到它在干什么（镜像窗），也能看到它每一步在想什么（思考流）
- 遇到支付、登录、验证码——它**主动交给你**：一点「接管」，它正在操作的那个界面整个搬到你面前，你处理完点「返回后台」，它接着在你离开的地方继续

## 二、两种工作模式

| | 工作区模式（默认） | 协同模式 |
|---|---|---|
| agent 看哪块屏 | 自己的虚拟工作区 | **你的屏幕** |
| 会动你的界面吗 | 不会 | 只在条件满足时出手 |
| 典型任务 | 打开美团搜火锅、跨应用找东西下单 | 打开相机，有鸟飞过就按快门 |
| 开关 | 一直可用 | App 里「主屏监控」开关，默认关 |

协同模式是给"等到某个条件就出手"这类需求准备的。相机取景、直播画面这些东西只存在于你的屏幕上，虚拟工作区里没有——所以必须能看着你的屏幕干活。

## 三、六个关键判断

这是这个项目最值钱的部分，不是功能列表。

### 1. 接管 = 搬任务，不是开新实例

朴素做法是「在主屏重新打开这个 App」。但那意味着：

- 状态全丢（搜索结果没了、导航卡在加载页）
- 后台多一个实例
- 你看到的是全新首页，不是 agent 刚干到的地方

正确做法是 `am display move-stack <taskId> <displayId>`——**把那个任务本身搬到另一块屏**。同一个实例换块屏显示，状态原封不动。

```
126(虚拟屏) → 点接管 → 0(主屏) → 点返回后台 → 126(虚拟屏)
```

### 2. 有些需求不该用 VLM 每帧硬怼

- **相机监控等鸟**：30fps，而一次视觉模型调用要 1.5–2 秒。按"每两秒看一眼"做，鸟早飞了。这类需求应该走本地轻量目标检测（单帧 ~10ms），模型只在"要不要调参数"这种时候出场。
- **直播弹幕**：主播说「抠 234」就发弹幕——这个需求**连视觉都不需要**，需要的是流式 ASR + 关键词匹配。

能做出"这里不该用大模型"这个判断，比多做一个功能有价值。

### 3. 点不到的按钮，别卷视觉精度，换 Intent 直达

努比亚记事本的「新建」加号不在无障碍树里（App 设了不导出），视觉定位永远救不了。但它的编辑页 Activity 是可以直接拉起来的：

```
am start -n cn.nubia.notepad.preset/cn.nubia.notepad.NotePadEditorActivity
```

扫出目标 App 的 Activity 清单 → 按名字关键词找目标页面 → 用 Intent 一步直达，**完全绕开 UI 导航和坐标猜测**。

这条还顺带治了一个严重事故：agent 点不到加号，退而在已有笔记里打字，把用户原文覆盖了。有了直达，它根本不需要碰已有条目。

### 4. 动作执行成功 ≠ 起了作用

点快门返回 `ok`，但照片根本没出现。靠"执行结果"判断是不够的，必须**验证**：

```
点快门 → 比对相册最新文件名 → 没变就补发系统相机键 → 再验一次
```

最终日志：`点快门没拍成 → 补发系统相机键，结果：已拍下 IMG_...jpg`

> 相机快门用屏幕坐标点不稳（模型给的归一化坐标换算后总差一截，无障碍 ACTION_CLICK 也未必生效），**系统相机键 `input keyevent 27` 一定能拍下去**。

### 5. 意图交给模型判断，不靠关键词 if-else

「用户这句话是任务还是问题？要不要看他的屏幕？」——这类判断早期用关键词匹配做，代价很直接：

```java
String[] keys = {"当", "一旦", "出现", "就拍", ...};
```

「打开微信，找到赵禹哲的聊天记录，里面**出现**任意商品就去京东买」命中了"出现"，被判成需要盯着用户屏幕的监控任务，直接被拦下要求开主屏监控——而它只是个普通的跨应用任务。

改成一次**纯文本 LLM 调用**做路由，返回严格 JSON：

```json
{"type":"task|question|correction|control", "mode":"background|main", "app":"...", "reply":"..."}
```

- `question`（只是提问）→ 直接回答，**不建屏、不截图、不调视觉模型**
- `task` → 进主循环，`mode` 决定用工作区还是主屏监控
- `correction` → 写进记忆区
- `control`（停止/接管）→ 直接执行，不用问模型

**关键工程决策**：模型没说话（没 key / 超时 / 返回非法 JSON）时**回退到规则**。路由在链路最前面，它挂了不能让整个 App 不能用人。

顺带一个成本上的收益：路由一次几十 token，主循环一次几千 token，用最便宜的模型做最简单的事。

### 6. 程序化记忆：把走过的路沉淀成技能

agent 每次都从零推理是浪费——手机上的操作路径高度可复用（打开 App → 点搜索 → 输入 → 点搜索）。

所以任务**真的做成了**之后（成功门控，只在判 finish 那一刻），把这一轮走通的动作序列存成技能：

```
技能 = { 应用, 动词, 起始页面指纹, 动作序列, 成功次数, 失败次数 }
```

下次同类任务进来，先检索技能库，**命中就照着走、跳过模型调用**。

三个必须守住的点：

- **技能是带参数的函数，不是固定脚本。** 动作序列里用 `{q}` 占位。否则"搜火锅"存进去，下次"搜烤肉"会输入火锅。
- **成功两次才转正。** 手机 App 会改版、会弹权限框，一次成功可能只是运气（Voyager 在 Minecraft 里一次就写，因为环境是确定的）。
- **优雅降级。** 命中也要每步校验，偏离立刻放弃、交还模型，连错两次自动淘汰——这就是"缓存失效"的处理。

对应的是 Voyager（2023）的技能库思路，以及 Agent S4「Evolving Agent Interfaces」（2026）里"让 agent 从任务经验演化它使用的接口"——沉淀出来的技能，本质就是给模型新增了一个高层动作。

## 四、硬骨头

### 跨屏启动的权限根因

最初「程序未能在虚拟屏打开」。查下来真因不是"这个 App 不可分屏"，而是 **display 的属主**：

- 虚拟屏由 `DisplayHost` 以 shell（uid 2000）身份创建
- App 是 uid 10xxx
- Android 的 `isCallerAllowedToLaunchOnDisplay` 不允许非属主往这块屏 `startActivity` → 被静默弹回主屏

**解法：启动一律走 shell 下发**（shell 才是属主）：

```
am start --display N -f 0x18000000 -n <pkg>/<组件>
```

组件名用 `PackageManager.resolveActivity(MAIN/LAUNCHER)` 现解析，应用内 Intent 只作兜底。

### 跨应用：三道锁

早期跨应用完全走不通（"先微信再京东"，京东被解析成微信）。三处代码把它锁死了：

1. **`forcedPkg` 用完没清**：它是跨任务存活的 `volatile` 字段，后面所有 `Launch` 都返回第一个应用的包名
2. **单应用上下文**：`currentPkg` 只有一个，节点清单、SoM 标注、直达页面全服务这一个包
3. **没有跨应用的信息传递**：商品名怎么从微信带到京东

解法：

- `forcedPkg` 用完即清
- **应用上下文跟随前台窗口**动态推导（`focusedPackage()` 取层级最高的应用窗口），切应用后节点清单自动跟着换——**不需要为任何应用写代码**，所以 N 个应用都一样
- **信息槽**：新增 `do(action="Remember", key="商品", value="...")`，每步提示里带上【已记住的信息】
- 多应用时按**在任务里出现的先后**选第一个（以前按 HashMap 顺序取，结果每次都不一样）

### 虚拟屏与主屏必须同尺寸同密度

接管时字体忽大忽小，根因是虚拟屏 720×1280@360dpi 而主屏 1216×2688@520dpi——任务跨屏发生配置变化，Activity 重新布局。

**解法：虚拟屏直接用主屏的像素尺寸和密度**，抓到的帧再等比缩回 720 宽给模型（上传体积不变）。

> 顺带踩了个坑：缩略**必须等比**。真实比例 1216:2688（0.45）硬缩成 720×1280（0.56）会把画面拉变形，模型看到的界面本身就是错的——这才是"点我的点到直播"的主因。

### 长任务永久卡死：JSON 控制字符

任务跑到 step 21 开始空输出。服务端报错：

```
JsonMappingException: Illegal unquoted character ((CTRL-CHAR, code 9))
  → messages[44].content
```

**code 9 = TAB**，出自小红书笔记标题。我们手写的 `jsonStr()` 只转义了 `"` `\` `\n` `\r`，漏了 0x00–0x1F 的其余控制字符。

**为什么是"永久"卡死**：那条带 TAB 的消息进了历史，之后每一步都发同一份非法 JSON——step 21/22/23 是一模一样的 400，直到步数耗尽。

修法三处：`jsonStr` 补全转义、节点 label 源头清洗、400 不再无脑重试（第 1 次丢最后一步，第 2 次只留最近一屏，第 3 次交给用户）。

### 不支持的动作 ≠ 模型不行

模型输出 `Long_press`（我们没实现）→ 返回 `err` → `fails++` → 连续 2 次**把主模型降级**。

但"模型用了我们没实现的动作"是我们的欠账。降级到更弱的模型只会让它更容易再输出不支持的动作——**负向螺旋**：doubao → glm → glm45，一路劣化到跑不动。

改成：返回 `unsupported`，把可用动作列表整段回给模型，**不计失败、不切模型**。

### 内置 shell 通道：两条血泪

免 Root 靠的是自己实现 adb 客户端（协议取自 Shizuku，Apache-2.0）。这里踩了两个坑，都表现为"命令莫名返回 null"，查起来极其费劲：

**① 绝不能在主线程调用。** 它是网络连接，Android 会直接抛 `NetworkOnMainThreadException`：

```
点「接管」→ takeover() 在主线程 → preGrant()/takeoverMoveToMain() → 走 shell
                                                    ↓
                                   NetworkOnMainThreadException
                                                    ↓
                      execFast 返回 null → 找不到任务 → 兜底"新开实例"
```

用户看到的就是"接管又开了个新应用、操作记录全丢"。凡是调用 shell 的地方都要挪进后台线程。

**② 连接不能复用。** 为了省握手做过一次"复用共享 AdbClient"的优化，结果 DisplayHost 的常驻进程占着那条连接的 shell 流，复用导致协议错乱（`not A_WRTE` / `EOFException`），**所有后续命令全部失败**——表现为虚拟屏上拉不起任何应用。改成每次新建、用完即关才对。

### 编号框画在了错误的坐标系

模型"认得出按钮却点不准"，查了很久发现：Set-of-Mark 的编号框用的是**屏幕像素**（0..1216），却直接画在**只有 720×1592 的缩略截图**上——框大半落到画布外，剩下的也全错位。模型照抄的是错框的中心。

**画布坐标和目标坐标不在同一尺度时，一定要显式换算。** 这类 bug 的阴险之处在于"识别全对、就是点不准"，很容易被误判成模型能力不行。

## 五、实测记录

| 场景 | 结果 |
|---|---|
| 美团「搜索火锅」 | 2–4 步，真实搜索结果页 |
| 微信「搜联系人填 123 不发」 | 草稿在输入框，未发送，输入法没弹到主屏 |
| 相册「搜索捷克相关照片」 | 成功 |
| 百度地图「导航到故宫」 | 进真实导航界面（15.3km / 1h26m） |
| 跨应用「先京东再微信」 | 两步都完成，撞安全验证主动接管 |
| 相机监控「有人出现就按快门」 | 前 3 轮判断不满足**一次都没乱点**，第 4 轮命中拍照成功 |
| 接管往返 | 126(虚拟) → 0(主屏) → 126(虚拟)，状态不丢 |

单次 API 延迟：关掉深度思考 + `max_tokens` 分档 + JPEG 传输后，**25.6s → 1.6~4.5s**。

## 六、已知边界

- **Shizuku 首次配对绕不过去**。Android 的安全边界：要拿 shell 权限就得先有一次 adb/无线调试授权，App 无法自我提权。配对一次之后全部自动（Shizuku 授权、无障碍绑定、虚拟屏创建都由 App 自举完成）。
- **延迟是 2 秒级**，不适合需要 200ms 内响应的场景（那种该走本地检测）。
- **部分 App 藏无障碍树**（抖音等），只能靠画面坐标，可靠性低于能读树的 App。
- **虚拟屏与主屏同尺寸**，抓帧后缩放，有固定开销。
- 步数上限 20–50 可调，每步约 1.3k token，成本由用户承担。

## 七、构建与运行

```bash
python build.py dev       # 开发版 0.14  → Wellphone-Dev-0.1.apk
python build.py release   # 正式版 1.2   → Wellphone-1.2.apk
```

两个变体 `applicationId` 不同（`local.wellphone.dev` / `local.wellphone.remote`），可同时装在手机上互不干扰。

依赖：

- Android 11（API 30）+
- [Shizuku](https://shizuku.rikka.app/) —— 提供无 root 的 shell 能力
- 视觉大模型 API（Anthropic 协议 / OpenAI 协议，App 内两套并存）

### 给使用者的安装步骤

> ⚠️ **必须先装 Shizuku**，这是硬依赖——Wellphone 靠它拿到无 root 的 shell 能力（跨屏启动、注入触摸、读无障碍配置都依赖这个）。没有 Shizuku，App 只能打开界面，执行不了任何任务。

1. 安装 [Shizuku](https://github.com/RikkaApps/Shizuku)（开源，免费）
2. 按 Shizuku 的引导启动它（需开启「开发者选项 → 无线调试」，用配对码配对一次）
3. 安装 Wellphone APK，打开 → 点「**一键准备**」
4. Shizuku 弹出授权请求 → 点「**允许**」
5. 之后全部自动：无障碍服务会在 App 内自动绑定，虚拟屏自动创建

一次性成本：Shizuku 的首次配对要用户手动做一次（Android 的安全边界，无法绕过）。**配对成功后，后续每次打开 Wellphone 都是全自动的。**

### 分发 APK 时注意

用微信/QQ 直接传 APK 时，对方收到的文件名常被改成 `.apk.1`（传输方为防止误安装加的后缀），无法直接点击安装。解决办法：

- 接收方把文件名改回 `.apk` 即可
- 或者发送前**打包成 zip**（zip 不会被改名，也更稳妥）

另外 Android 11+ 才支持。

### 自动化钩子（调试/演示用）

```bash
adb shell am start -n <pkg>/local.wellphone.remote.MainActivity \
  --es task "在美团搜索火锅" --ez autorun true
```

另有 `--ez diag true`（虚拟屏诊断）、`--ez watch true`（开主屏监控）、`--es stopText 123`（写到这词就停，安全阀）。

## 八、配置 API key

源码里 **不带任何密钥** —— `PROVIDERS` 的 `key` 是空字符串，运行时注入。

**最省事的办法：App 内点「API Key」按钮**，两个输入框分别填：

| 输入框 | 用在哪 | 为什么 |
|---|---|---|
| 豆包（火山方舟） | 主循环——看截图、输出动作 | 需要视觉能力 |
| DeepSeek | 意图路由、回答问题 | 纯文本就够，便宜且快 |

两个都只存本机 `SharedPreferences`，不会上传。填哪个就用哪个，改完立即生效。

> 早期版本靠写 `llm.json` 到 `/sdcard/Android/data/<包名>/files/` 注入。
> **实测在本机上 App 读不到这个目录**（adb 能往里写、App 读不出来），所以改成走 App 界面。
> 文件这条路现在仍保留作兜底，但不推荐用。

填完后点「大脑」按钮可以在 doubao / deepseek 之间切换主循环用谁，用来实测对比谁更快更准。

没配 key 时 App 不会默默失败——会直接提示「未配置 API key」并指出去哪里填（否则会一路 401 降级，看不出真正原因）。

`.gitignore` 已包含 `*.apk`、`*.jks`、`classes*/`、`dex*/`、`variant/`、`build.out`，以及 **含密钥的 `llm*.json` 和真机日志**。

## 九、项目结构

```
src/local/wellphone/remote/
  MainActivity       控制台、一键准备、记忆区
  Agent              模型循环、动作执行、跨应用、监控模式
  AgentService       无障碍服务：读屏、注入文字、手势、主屏截图
  DisplayHost        独立进程，创建并镜像虚拟屏（shell 身份）
  OwnedDisplay       与 DisplayHost 通信
  ShellChannel       Shizuku shell 命令通道
  ThinkingWindow     悬浮思考流 + 状态行
  MirrorWindow       主屏角落的工作区镜像
  MemoryStore        记忆区（应用别名/直达页/偏好/避坑/用户教导）
  SkillStore         程序化记忆（技能库）：沉淀并检索可复用的动作序列
  BuiltinShell       内置 adb 通道（免 Root、免 Shizuku）
  PairShellService   内置无线调试配对
  PairCodeReceiver   配对码输入
  Ui                 悬浮窗/镜像窗共用的样式工具（纯代码画 drawable）
  ControlReceiver    通知栏四个按钮
```

## 十、隐私

- 主屏监控**默认关闭**。关着的时候 agent 看不到你的屏幕。
- 打开后，通知栏常驻显示「⚠ 主屏监控已开」。
- 监控任务只在**用户明确说出"打开/启动"时**才会去开应用——「我屏幕上一旦出现地图就截屏」这种是纯监控，不该自作主张把地图打开。
